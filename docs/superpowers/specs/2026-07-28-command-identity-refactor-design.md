# Command identity refactor: separate item resolution from command definition

## Problem

A command's stored `CommandDescriptionData` (verb + adjective + noun) currently serves three unrelated jobs at once:

1. **Runtime matching criteria** — what the player must type for the command to fire.
2. **Grouping/chain identity** — which `CommandData` variants belong to the same `CommandChainData`.
3. **Persistence and UI identity** — the literal map key in `CommandProviderData.availableCommands: Map<String, CommandChainData>`, *and* the literal `:commandId` route parameter used to open a command in the editor.

For commands that live on an `Item` (overwhelmingly the auto-generated take/drop pair, but also any custom command an author attaches to a specific item), the adjective and noun are **copied from the item's own description at generation time** — `ItemEditorView.getRawCommandData` builds `new CommandDescriptionData(verb, itemDescription.getAdjective(), itemDescription.getNoun())`. That's the duplication: the item already declares its own noun/adjective; the command re-declares them, and nothing keeps the copy in sync when the item's description changes. `01kt1n50059gxqmq7q03rt5b0x`'s `"get|neoprene|suit"` key is exactly that stale copy — the identity should never have depended on the item's current adjective at all.

Because that string also *is* the persistence key and the UI identity, the same duplication causes two more problems the investigation surfaced:

- **Orphaning** (the bug fixed 2026-07-28): changing the item's adjective makes the old map entry unreachable by the cleanup logic, leaving duplicate stale commands. Patched narrowly by matching on verb instead of full spec — but the underlying design (identity = mutable text) is still there for every other case that touches it.
- **Chain collapse** (newly found, not yet fixed): `CommandEditorView.swivelTheSaveButton()` deletes the *entire* old map entry (`availableCommandsHelper.remove(commandId)`) whenever a command's verb/adjective/noun changes, and always constructs a brand-new `CommandData` rather than relocating the edited one — so editing one command out of a multi-command chain silently discards its siblings. `CommandsMenuViewTest.java:158-185` already sets up exactly this scenario; nothing currently guards against the regression because the identity model makes "the same chain, renamed" indistinguishable from "a different chain."

Both are symptoms of the same root cause: **identity is derived from mutable, duplicated data instead of being its own stable thing.**

## Scope confirmed by codebase research

- `GenericCommandProvider` (runtime BO) and `CommandProviderData` (persistence DO) use *isomorphic* keys — a `GenericCommandDescription`'s `equals`/`hashCode` are computed purely from verb+adjective+noun, so the BO map has the exact same fragility as the DO map, not just a persistence-layer quirk.
- `ItemIdentifier.findItems` already resolves *which item* a player's noun/adjective refers to, independently of any command — using the item's live `getNoun()`/`getAdjective()`, not anything stored on a command. Item resolution and command matching are already two different code paths; they just don't admit it.
- `Item`/`ItemData` already carry a stable ULID (`BasicData.id`), and so do `CommandData` and `CommandChainData` — **all completely unused as identity today**. The infrastructure this refactor needs already exists in the schema; it's just not wired up as the map key.
- Directions (`DirectionData.commandData`, one command, no map) and Workflow (`WorkflowData.commands`, a flat list feeding a `TreeMap<CommandDescription,Command>`) don't have the *persisted-map* half of this problem — but Workflow commands' `TreeMap` ordering still runs through the same string-shaped `compareTo`. Out of scope for the orphaning/collapse bugs specifically, but worth keeping in mind since they share the underlying `CommandDescriptionData` type.
- The identity leak isn't confined to `server/mapper`/`server/parser`: `CommandsMenuView`, `CommandEditorView`, `CommandViewModel`, and their routing tests all treat the spec string as a first-class UI identifier (route params, grid row keys). `LocationUsageTracker`/`ItemUsageTracker` use it for display text only (low risk). `GridUnbufferedInlineEditor` and `SimpleCommandDescription` are dead code that also parse spec strings — worth deleting while in the area, not part of the fix.

## Approaches considered

**A — Verb-only identity for item-owned commands, via wildcard-noun matching.**
Stop copying the item's adjective/noun into auto-generated (and by convention, any item-scoped) commands at all; store them empty. Relax `GenericCommandProvider`'s noun comparison to treat an empty *stored* noun as a wildcard (mirroring the wildcard rule verb and adjective already have) — matching then works because `ItemIdentifier` already resolved the specific item by its live noun/adjective before we ever look at that item's own command list, so re-checking noun there is redundant anyway. Cheapest change, and it's exactly what was asked for ("it should only use `get`"). Doesn't by itself fix chain collapse, because the map key would still be derived text (now usually `"get||"` instead of `"get|neoprene|suit"`) — smaller, but the same kind of key.

**B — Split item-owned commands into a structurally separate, non-keyed list.**
Give `ItemData` its own `List<CommandData>` for item-scoped commands (no map, no spec key at all — mirroring how `DirectionData` already has exactly one unkeyed command). Considered and rejected as the primary fix: it forecloses an item ever having more than one *chain* per verb (e.g. an author-authored precondition-gated variant alongside the auto-generated one), which the current "Command Chain" feature explicitly supports and which nothing here needs to break.

**C — Stable opaque ID as the identity, decoupled from all vocabulary text.**
Use `CommandChainData.getId()` (already exists, already a ULID, currently unused) as the `CommandProviderData` map key and as the `:commandId` route parameter, instead of any derived string. Grouping ("does this new command join an existing chain?") becomes a creation-time decision only — made once, using verb (+ adjective/noun where that's meaningful), never re-derived afterwards. This is what fixes chain collapse, and it's what makes the UI-routing layer stop depending on vocabulary text at all.

**Recommendation: A + C together, staged.** They're complementary, not competing — A removes the *duplication* (the thing that was actually reported as wrong), C removes the *fragility of using derived text as identity* everywhere else that pattern still exists (persistence key, route param, chain grouping). Doing only A leaves a smaller but structurally identical problem in place (`"get||"` is still a derived-text key that a future verb rename would orphan the same way). Doing only C leaves the item's command still privately duplicating its own adjective/noun in storage — technically stable, but not what was asked for, and it wastes the one piece of information (`ItemIdentifier` already resolved the item) that makes the duplication removable in the first place.

## Design

### 1. Matching: item-owned commands no longer restate the item's adjective/noun

- `ItemEditorView.getRawCommandData` (and the equivalent construction path anywhere else that builds an item-scoped command) stops passing `itemDescription.getAdjective()`/`getNoun()`. Item-scoped `CommandDescriptionData` carries verb only; adjective/noun are `VocabularyData.EMPTY_STRING`.
- `GenericCommandProvider.getMatchingCommandChain`'s noun comparison gains a wildcard rule, but *only* on the stored side: `itemNoun.equals(noun) || EMPTY.equals(itemNoun)`. This is deliberately **not** symmetric with the verb/adjective wildcard rule (which allows either side to be empty) — an empty *queried* noun must NOT match a stored non-empty noun, or a bare verb-only input (e.g. "go" with no direction) would ambiguously match every direction command in the location instead of correctly falling through to "I don't know how to do that." Confirmed empirically: applying the symmetric formula passes the full suite unchanged (no test covers a bare-verb multi-direction location) but silently changes that fallthrough to "What do you want to go?" — a real, unreviewed behavior change for location/workflow commands, which are explicitly out of scope (see "What this does *not* change" below). The asymmetric rule is additive and safe: it only starts matching cases that previously matched nothing (an empty stored noun previously matched only an empty query noun, which no real command chain intentionally relied on).
- Non-item-scoped commands (workflow, location-level ambient/direction-triggered commands) are unaffected in *behavior* — they continue to declare real adjective/noun when that's meaningful, and the wildcard rule simply never triggers for them since their stored noun isn't empty.
- `CommandExecutor.reduceCommandChains`'s adjective-based disambiguation stays as-is; it now naturally has less work to do for item-owned chains, since disambiguation between two items sharing a noun already happened correctly upstream in `ItemIdentifier` using the items' *live* adjectives — it never needed the redundant copy.

### 2. Identity: `CommandChainData.id` becomes the real map key

- `CommandProviderData.availableCommands` stays `Map<String, CommandChainData>`, but the `String` is `CommandChainData.getId()` (a ULID, already generated on construction via `BasicData`), not `getCommandSpecification()`.
- `CommandProviderData.add(CommandData)` groups by **matching an existing chain's trigger description** (verb, and adjective/noun where the command actually declares them) only when deciding whether to create a new chain or append to one found by that match — then keys the result by that chain's own stable id, permanently. Renaming the trigger afterwards (verb, or for non-item commands, adjective/noun) edits the chain's trigger description in place; it never changes the chain's id or requires moving entries between map slots.
- `CommandEditorView`/`CommandsMenuView`'s `:commandId` route parameter and grid row keys switch from the spec string to the chain id. (`WorkflowEditorView` has no `:commandId` route parameter — its route is `author/adventures/:adventureId/workflow` with no per-command deep link — so it needs no change here.) `swivelTheSaveButton()` simplifies to "look up the chain by id, update the command in place" — the delete-and-recreate branch that causes chain collapse goes away because there's no longer a reason to move a chain between map slots when its trigger changes.
- `ItemEditorView.removePickupCommands`/`createPickupCommands` simplify further than the current verb-based patch: since item-owned commands now always have empty adjective/noun, the take/drop chains are unambiguously identified by verb alone regardless of the item's description, past or present — the lookup this refactor needs is strictly simpler than what exists today, not more complex.

### 3. Persistence migration

- Existing Mongo documents have string-keyed maps today. Migrate **lazily on load, not with a batch script**: `CommandProviderMapper.mapToBO` detects a legacy key (doesn't match the DO's own `CommandChainData.id` — true for every document written before this change) and re-keys it to the chain's id in memory; the next save persists the corrected shape. No separate migration script, no downtime, no risk of a batch job touching adventures currently being edited. A one-off audit query (not a mutation) can confirm convergence later if desired.
- Item-owned commands' stored adjective/noun get cleared to empty the same way — lazily, the next time `ItemEditorView` regenerates pickup commands for that item, or eagerly for auto-generated ones as part of the same load-time normalization if we want it to happen without waiting for an edit. Recommend eager normalization at load time for auto-generated commands specifically (detectable: verb equals the take/drop word, actions match the known take/drop shape) — the demo adventure's neoprene suit is exactly the kind of already-drifted data this needs to self-heal, without another manual `mongosh` cleanup.

## What this does *not* change

- The Command Chain feature itself (multiple variants of one trigger, tried in order until preconditions pass) — untouched, still exactly as documented in the handbook.
- Workflow and location-level ambient commands — still keyed and matched by full verb+adjective+noun, because for them (unlike item-owned commands) that's real, non-duplicated information.
- Any public-facing behavior an author would notice, other than: the two bugs going away, and (as a side effect of the id-based key) the "Command Chain" grid in `CommandEditorView` no longer needing the item's adjective/noun to stay put when it's edited.

## Staged implementation plan

Each stage is independently testable and shippable; later stages depend on earlier ones but not vice versa.

1. **Matching wildcard rule.** Add the empty-noun wildcard to `GenericCommandProvider.getMatchingCommandChain`. New unit tests: an item-owned-style command with empty noun matches any queried noun; a location/workflow-style command with a real noun is unaffected. Run the full suite — this is the change most likely to have a hidden dependent, so it goes first and alone.
2. **Stop copying item description into auto-generated commands.** Change `ItemEditorView.getRawCommandData` (and `createPickupCommands`/`removePickupCommands`, which can now key purely on verb with no fallback needed) to store empty adjective/noun. Update/extend the existing `ItemEditorViewTest` regeneration test to assert the stored commands carry no adjective/noun, not just that stale duplicates are gone.
3. **Chain identity switch.** Change `CommandProviderData`'s grouping/lookup to use `CommandChainData.getId()` as the map key, with creation-time-only grouping by trigger description. Update `CommandMapper`/`CommandChainMapper`/`CommandProviderMapper` accordingly, including the lazy re-key-on-load normalization. This is the largest single stage — cover it with mapper round-trip tests (legacy string-keyed fixture in, id-keyed out, chain contents unchanged) before touching any UI code.
4. **UI routing cutover.** Switch `CommandEditorView`, `CommandsMenuView`, `WorkflowEditorView`'s `:commandId` usage and `swivelTheSaveButton()` to the chain id. Update `CommandEditorViewRoutingTest`, `CommandsMenuViewRoutingTest`, `CommandsMenuViewTest`, `CommandViewModelTest` (the tests that currently assert against literal spec strings as identity — display-oriented assertions in `LocationUsageTracker`/`ItemUsageTracker` stay as they are, they format text, they don't use the string as a key). Add a regression test reproducing the chain-collapse scenario (`CommandsMenuViewTest.java:158-185`'s two-command-one-chain setup, edit one command's verb, assert the sibling survives) — this is the test that proves stage 3+4 together actually fixed it.
5. **Delete dead code.** `GridUnbufferedInlineEditor` and `SimpleCommandDescription` (confirmed no production callers) — remove along with their tests, since they're spec-string relics with no purpose once this lands.
6. **Demo-adventure verification.** Re-check `01kt1n50059gxqmq7q03rt5b0x` after stage 2+3 land and the item is next saved (or force the eager load-time normalization from the Persistence migration section) — confirm its pickup commands end up keyed by a stable chain id with empty adjective/noun, not `"get|neoprene|suit"`.

## Risks / things to verify empirically, not just by reasoning

- The noun-wildcard relaxation (stage 1) is shared code (`GenericCommandProvider`) used by every `Thing` — locations, items, containers. The full suite is the actual proof it's safe, not this document.
- `Workflow`'s `TreeMap<CommandDescription, Command>` ordering depends on `compareTo`, which is string-shaped but untouched by this plan (workflow commands aren't item-owned, so they're out of scope) — confirm stage 1's wildcard change doesn't leak into `Workflow` matching, since `Workflow` doesn't go through `GenericCommandProvider.getMatchingCommandChain` at all (it's a direct `TreeMap` lookup) and should be unaffected, but worth an explicit test given how central that class is.
- `AllItemsMenuView`, `CommandsMenuView`, and any other grid that renders a command's adjective/noun columns for an item-owned command will start showing **blank** cells instead of a copy of the item's adjective/noun after stage 2 — worth confirming this reads correctly in the running app (likely fine/better, since the item's own noun/adjective is already shown on the item's own row) rather than looking like missing data.
